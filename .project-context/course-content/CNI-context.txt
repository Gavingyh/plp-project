2. DAY-BY-DAY CONTENT
 
--- DAY 1 AM — Understanding & Designing Conversational UIs ---
Foundations:
- CUI = interaction through natural language instead of GUI elements ("just say what you want").
- Overlapping names: chatbot, virtual assistant, conversational agent, dialogue system,
  conversational platform (market vs implementation labels).
- Use cases: customer service, sales/marketing, IT service desk, HR, commerce, enterprise-software
  front end, advisory services (Accenture "Chatbots Are Here to Stay").
- Four common classes (overlapping, not architectures): Informational (FAQ bots), Transactional
  (booking, ordering, transfers), Enterprise Productivity (KPIs, scheduling), Device Control
  (smart home, car, wearables).
- Core concepts: intents, parameters/slots, actions, responses, contexts, events, goal, state.
- Two architectures: Modular pipeline (NLU -> Dialogue Manager -> NLG; testable, controllable,
  more engineering) vs End-to-end LLM (history -> LLM -> response; flexible, less effort, less
  control, needs guardrails).
 
How humans converse (design foundation — breaking norms erodes trust):
- Turn-taking cues: sentence structure, intonation, pauses, gaze/body language; interruptions.
- Speech acts (Austin/Searle): representatives, commissives, directives, declarations, expressives
  — bot responses are speech acts too ("OK" vs "I'll do that now").
- Conversation organisation: adjacency pairs (Q->A, greeting->greeting, request->compliance/refusal),
  side sequences (repairs, clarifications), opening/closing sequences.
- Initiative: system-led, user-led, mixed initiative (support side questions, corrections, return
  to task).
- Grice's Cooperative Principle mapped to bot design: Quality (don't hallucinate), Quantity (not too
  much/little), Relevance (stay on topic, don't re-ask), Manner (plain, concise, orderly).
 
Conversation design process (7 steps; designer = screenwriter, character creator, architect, UX
writer):
1. Is conversation the right fit for the task?
2. Gather requirements — users (needs, phrases, triggers), technical capabilities (identity,
   in/out-of-scope actions, permissions, cancellation, progress saving, data access), key use cases
   (most impactful first). Tip: capture users' own phrases as design/test examples.
3. Create a persona — adjectives -> 4-6 traits -> character -> role/strengths/limits -> voice
   (example: "Ola" salon scheduling assistant, personality spectrum).
4. Write sample dialogs — everyday language, variation; components: greetings, endings, questions,
   acknowledgements, confirmations, apologies, error prompts, suggestions, discourse markers,
   chips/buttons, earcons. No monologues. Question focus: narrow for specific info, wide for
   exploratory. Context sources: previous turns, screen, external (location/time/device), user profile.
   Confirmation: implicit (low risk), explicit (high risk/irreversible), reconfirmation (details
   changed after consent) — match effort to cost of misunderstanding. Happy path first, then errors.
   Repairs — system-initiated: No Match (1st: brief reprompt; 2nd: add options/examples; then exit
   gracefully with alternatives), No Input (audio), System Error (transparent, non-technical),
   ambiguity confirmation, slot validation. Golden rule: always leave the user a clear next step;
   never repeat a prompt verbatim. User-initiated: explicit correction (overwrite state, acknowledge
   the change explicitly), mid-flow interruption (push current flow to stack, answer, resume).
5. Test & iterate — role-play, simulators, watch confusion/frustration; change based on behaviour.
6. Long tail — 20% of paths serve 80% of users; minimal viable handling for rare paths.
7. Scale across devices/modalities (phone, speaker, watch, car, display) — bridge to Day 2.
 
--- DAY 1 PM — Building & Evaluating Conversational UIs ---
Modular pipeline under the hood (NLU -> DST -> Policy -> NLG):
- NLU: domain identification (optional), intent detection, slot filling -> semantic frame
  e.g. BookFlight(dest=London, date=tomorrow).
- Intent detection: deterministic (FST/keyword templates + NER + dictionaries; precise, brittle) vs
  ML text classification (BoW/TF-IDF, POS/deps, word/contextual embeddings; SVM/LR/RF/CNN/BiLSTM;
  context from past N turns helps).
- Slot filling as BIO sequence labelling: regex/dictionaries -> CRF -> BiLSTM+CRF.
- Dialogue State Tracking: running belief of goals/slots across turns; handcrafted vs statistical.
  State is more than filled slots: task facts, interaction progress (pending question, suspended
  task), action status (draft/confirmed/executing/completed/uncertain). Update rules: new info (add +
  keep source), correction (replace + invalidate dependent checks), side question (retain task),
  cancellation (stop, verify anything already sent).
- Dialogue policy: handcrafted decision trees vs statistical classifier over encoded state. Action
  types: task-independent (ask, confirm, clarify), task-specific (search, book, cancel), interface.
- NLG: template-based (predictable, rigid) vs neural (natural, risk of wrong output); hybrid =
  templates for critical status, generation for explanation.
- Pipeline: interpretable, testable, precise; but rigid, labour-intensive, hard to scale domains.
 
From modular to LLM & agentic CUIs:
- Why move beyond: language variety, knowledge work, multi-step action. "LLMs expand the interaction
  space; agentic control expands the action space."
- Three architectures: Modular pipeline (stable, high-control) / LLM-assisted CUI (LLM
  understands/drafts, retrieval supplies evidence, application owns flow) / Agentic CUI (model
  selects tools/steps, observes, adapts, stops/escalates). Rule: use the LEAST autonomous
  architecture that handles the task's real variability.
- LLM alone is not enough — challenges per CUI class: hallucination, no real-time/proprietary
  knowledge, bias, tool use & auth, multi-turn state, prompt injection, integration, privacy/
  compliance, latency. A useful LLM is grounded, connected and bounded.
- Structured prompting: system / user / assistant roles.
- RAG & memory: key facts/preferences, conversation history (sliding window or summary), extracted
  info, external knowledge.
- Long context is not all you need (Databricks long-context RAG study). Context engineering —
  failures: poisoning, distraction, confusion, clash; tactics: RAG, tool loadout, pruning,
  summarisation, offloading.
- Tool calling: developer supplies API specs/descriptions -> LLM emits schema-matching JSON ->
  results flow back. Never claim success from the proposed call; confirm from the tool result.
- Corrections/cancellation/resumption must hit application state; tool failures: explain invalid
  input, check completion before retrying unknown outcomes, bound retries and offer handoff.
- Guardrails at three points: input & intent (injection detection, PII filtering, off-topic),
  context & action (scope docs/tools, least privilege, approval for costly actions), output &
  outcome (validate claims vs evidence, toxicity, leakage). Ongoing monitoring + red-teaming.
  Tools: NeMo Guardrails, LlamaGuard, Guardrails AI.
- Agentic: from "answer my question" to "accomplish my goal". Agent = Model + Harness (system
  prompts, tools/skills/MCPs, infrastructure, orchestration, hooks). Controlled observe-reason-act
  loop. Agent may decide: missing info, whether to clarify, which permitted tool, arguments, next
  step, stop/escalate. Application must control: tool availability, permissions/credentials,
  approval, validation, max steps/time/cost, logging/audit. Components: LLM, instructions+policy,
  orchestrator | conversation state, task state, knowledge/RAG | tools, guardrails, monitoring.
  "An agent is an application architecture, not an LLM with a longer prompt." Keep the user in
  control (clarify, preview consequential actions, progress updates, report partial completion)
  without narrating chain-of-thought.
- Frameworks: CrewAI, AutoGen, LangGraph (graph control flow; workflows vs agents); trade-offs:
  convenience vs flexibility, complexity, lock-in.
 
Evaluating CUIs ("a single score is NOT enough"; evaluate continuously, and after any change to
model/prompt/tools):
- Perspectives: performance, diagnostic, user experience.
- Subjective: SASSI questionnaire — system response accuracy, likeability, cognitive demand,
  annoyance, habitability, speed (Likert).
- Objective bot analytics: goal completion, completion time, fallback rate, miss messages; message
  and user metrics (active/new/engaged users, retention). Insufficient for tool calling, state,
  context.
- RAG metrics: retriever — Hit Rate@K, Precision@K, Recall@K, MRR; generator — faithfulness/
  groundedness, answer relevance, answer correctness, semantic similarity.
- Human eval: SSA (sensibleness + specificity), Chatbot Arena (blind pairwise, Elo).
- LLM-as-judge: grading rubric in prompt (criteria, output schema, few-shot); dimensions:
  correctness, relevance, completeness, clarity, faithfulness, hallucination, safety, PII,
  coherence, consistency, instruction following, tone. Frameworks: G-Eval, DeepEval, Ragas,
  TruLens. Biases: inconsistent scoring, weak fine-grained distinctions, version sensitivity,
  verbosity, narcissistic (self-preference), authority bias. Mitigate: multiple judges, calibrate
  against human scores, version-lock judge.
- Multi-turn eval: state-tracking accuracy, flow/context maintenance, trajectory-based evals,
  simulated-user testing, failure modes (instruction drift, context saturation, wrong tool after
  state change). Specify expected behaviour BEFORE running; reuse scenarios as regression tests.
  Diagnose the responsible layer before changing the prompt.
- Conclusion: reliable CUIs combine natural interaction with explicit state, boundaries and evidence.
 
--- DAY 2 — Multimodal LLMs: Image and Document Intelligence (Explain / Select / Build / Evaluate) ---
Intro & landscape:
- Modality = form of information; course scope is images, document pages and text.
- Value: ask directly about visual evidence instead of describing/re-keying it; structured
  extraction; visual page search. Four capability families: describe, extract, answer/compare,
  retrieve. Evidence vs inference (image supports what's visible, not e.g. an exact date).
- Three usage patterns: one image -> VLM; one document -> document workflow (fields/summary);
  a collection -> retrieve pages then VLM with citations. Use the simplest pattern that preserves
  the evidence.
- Evidence contract in prompts: use only attached page, cite page/region per value, return null +
  reason if unreadable.
- Failure modes: invented objects, misread small text, counting/spatial errors, confident but
  unsupported answers (POPE).
- When to use multimodal: plain text sufficient -> text LLM; layout/handwriting/chart matters ->
  vision/structured extraction; many visual pages -> retrieval + selected pages; exact numeric data
  exists -> use the data + deterministic tools. Balance evidence vs latency, cost, privacy.
 
Foundations — pixels to representations:
- Visual tokens are feature vectors, not vocabulary IDs. Continuous visual embeddings (ViT
  understanding) vs discrete codebook tokens (token-based image generation, e.g. Chameleon).
- Perception (read text, locate objects, recover layout) vs reasoning (compare, apply rules,
  aggregate) — separable but can fail together.
- Input pipeline: decode (JPEG/PNG, EXIF orientation, alpha, colour space) -> geometry policy
  (stretch / resize+crop / resize+pad / tile-AnyRes, each with trade-offs) -> tensor + normalisation
  (use the processor paired with the checkpoint; CLIP mean/std, not ImageNet) -> patches
  (224x224, P=16 -> 196 tokens) -> linear patch embedding + position (+ class token) -> ViT
  self-attention contextualises tokens -> connector/projector matches LLM width, may pool tokens.
- Dynamic resolution: LLaVA-NeXT AnyRes (tiles + global view) and Qwen2-VL native dynamic
  resolution (2D position, token budgets). More detail = more tokens = more memory/latency.
- Prompt requests behaviour; the pipeline controls visual evidence.
 
CLIP deep dive (alignment before generation):
- Dual encoder (image tower + text tower, no cross-attention), project + L2-normalise into a shared
  space, cosine similarity. Contrastive training: N matched pairs on the diagonal, N^2-N in-batch
  negatives; symmetric loss (image->text row softmax, text->image column softmax).
- Zero-shot classification: encode class prompts, argmax similarity. Prompt engineering matters
  ("a photo of a dog", disambiguating crane/seal/bank); prompt ensembling averages templates.
- Bidirectional retrieval; contrastive objective more data-efficient than caption prediction.
- Limits: one global vector loses small text, counts, local relations; strong for semantic retrieval,
  open-vocab classification, filtering, fast indexing; weak for exact OCR, counting, spatial chains;
  no decoder so it cannot generate text.
 
Generative VLMs — LLaVA deep dive:
- Architecture: CLIP vision tower -> projector W -> LLM; image enters as projected visual vectors
  interleaved with text tokens.
- Training: Stage 1 feature alignment (~595K CC3M pairs; only projector trained) -> Stage 2 visual
  instruction tuning (LLaVA-Instruct-158K GPT-4-generated conversations; projector + LLM, vision
  frozen). Separates interface learning from behaviour learning.
- LLaVA-1.5: CLIP ViT-L/14 @336px, two-layer MLP connector, 665K data mixture — better recipe
  can matter as much as complexity. LLaVA-NeXT: AnyRes for detail; token budget trade-off.
- Domain adaptation: keep vision frozen first, LoRA/projector tuning on image-instruction-answer
  records; for docs add OCR-aware data or higher resolution (LLaVAR). Measure OCR, grounding and
  hallucination separately.
- Failure causes: hallucinated objects (LLM prior), missed small text (resize/token budget), wrong
  relations, verbose-incomplete, unsafe/biased. A bigger LLM doesn't fix a missing visual signal.
- Document models: LayoutLMv3 joins text tokens + 2D boxes + image patches in one Transformer
  (MLM, MIM, word-patch alignment objectives). Donut for OCR-free extraction.
 
Multimodal RAG:
- Retrieve pages, then reason — don't make the generator read the whole archive.
- Two clocks: offline ingestion (render, OCR/visual encode, store vectors + metadata, re-run on
  change) vs online query (encode, retrieve + rerank, package evidence, grounded answer).
- Page identity must survive every stage (file -> page -> region -> vector -> citation IDs); never
  reconstruct citations from rank order.
- Retrieval unit: page-level (layout, simple provenance, dilutes small evidence) vs region/chunk
  (precision, more entries, needs segmentation).
- Lexical index (exact terms/IDs, fast, needs OCR) vs visual index (charts/layout, OCR-free, costly).
- Dual-encoder offline indexing + ANN search; global page vectors fast but blunt.
- ColPali: page image -> many patch vectors, query -> token vectors, late interaction MaxSim
  score(q,d) = sum_i max_j q_i·d_j. Trades storage/compute for fine-grained relevance.
- Rerank a recall-oriented short list; hybrid lexical (BM25) + visual with normalised/fused scores —
  fusion weights need evaluation, not intuition.
- Evidence packaging: page label next to each image, deterministic order, limit irrelevant images.
- Grounded generation contract: answer only from supplied pages, cite page_id per claim, abstain if
  absent/unreadable, return JSON schema. Citations are data (file_id + page_id [+ bbox]), not
  decoration.
 
Reliability & evaluation:
- Evaluate retrieval before answer quality; debug from the earliest failing stage (render -> index
  -> retrieve -> reason -> format); change one component at a time; keep traces.
- One accuracy number hides four systems: input quality, retrieval, perception+reasoning, output
  validation.
- Benchmarks != product fitness: MMMU (expert multi-discipline), DocVQA (layout-dependent reading),
  POPE (yes/no object-hallucination probes with random/popular/adversarial negatives).
- Build task slices (small text, tables, charts, handwriting, multi-page) before averaging; include
  abstention cases.
- Controlled ablations: vary one of model / retriever / resolution / prompt while holding others.
- Metrics: Recall@k (coverage), MRR / nDCG (ranking); answers — normalised exact match, accuracy/F1,
  claim rubric, schema + field accuracy (valid JSON can still be wrong). Calibration: does stated
  confidence match empirical accuracy; set abstention thresholds by risk.
- Human review of claims vs citations; a disciplined ~30-example test set (define slices, write
  expected evidence pages first, freeze, don't tune and report on the same examples).
 
--- DAY 3 — Speech Processing Basics, ASR/MT, and Speech+NLP Case Studies ---
Framing: spoken human-machine interaction is still commonly a pipeline (ASR -> NLU/LLM -> TTS),
though end-to-end systems (speech-to-intent, direct speech-to-speech) are emerging. Extended
scenarios: speech-to-speech translation (ASR -> MT -> TTS), image/document translation with voice
output (OCR -> MT -> TTS), assistive tech (OCR -> TTS for visually impaired; ASR -> MT -> TTS for
cross-lingual meetings).
 
Topic 1 — Speech signals and features:
- Speech captured by microphone, stored as a sequence of numbers (1-D signal); converted to a
  spectrogram (2-D: frequency strength over time) for analysis. Different phones show different
  energy at different frequencies (AA/IY/UW/M examples).
- Frames: signal processed in segments — frame size typically 20-25 ms, frame shift 10 ms, frames
  overlap. Each frame -> one feature vector, so speech = sequence of feature vectors.
- Common features: MFCCs (short-term power spectrum on the nonlinear mel scale; captures phonetic
  content; standard for speech/speaker recognition) and LPC (spectral envelope, predicts current
  sample from previous ones, estimates formants; used in compression/synthesis/recognition).
  Typical inputs: 39-dim MFCC, 80-dim filter-bank output, or 400 raw sample points.
- Information in speech: Content (what is said -> ASR/TTS), Timbre (who said it -> speaker info),
  Prosody (how it is said), plus environmental info (indoor/outdoor, quiet/noisy).
- Prosody: perceived as intonation, lexical tone (e.g. Mandarin's four tones), emphasis, emotion,
  phrase breaks; acoustically = fundamental frequency (F0/pitch), duration, energy. Voiced signals
  (vocal cords vibrate, periodic — all vowels, /z/, /v/) vs unvoiced (noise — /s/, /f/); pitch
  exists only in voiced signals, frequency = 1/period.
- Preprocessing: Voice Activity Detection (find valid speech segments), speech enhancement (noise
  reduction), normalisation (time and frequency domain).
- Digitisation (appendix): analog pressure wave sampled at regular intervals. Ear hears ~50 Hz-15 kHz,
  so Nyquist says ~30 kHz+ to keep everything; CD = 44.1 kHz; in practice 8 kHz (telephony) and
  16 kHz (PC/smartphone). Quantisation: 16-bit PCM (-32767..32767) is the speech standard; A-law
  (Europe) / mu-law (US, Japan) are 8-bit logarithmic codes that keep quiet sounds better.
  Formats: WAV (uncompressed PCM, lossless), MP3 (lossy), FLAC (lossless), OGG (container); speech
  input is normally uncompressed PCM, and ASR models are built for a specific sampling rate.
- Recording quality: microphone quality, ambient noise, recording level (too low = lost
  resolution, too high = clipping).
 
Topic 1 — Tools:
- Audio software: WaveSurfer (open-source visualisation), Adobe Audition (professional editor),
  Audacity (free editor/recorder), SoX (command-line: `sox --i` info, `-r 8k` resample, `-c 1`
  mono, raw->wav, concatenate, `speed 1.1`).
- Python: Anaconda/Spyder/Jupyter; SoundFile, Wave, scipy.io.wavfile, audioread (read/write);
  PyAudio, SoundDevice (play/record); LibROSA (feature extraction, spectrogram display, effects —
  e.g. librosa.stft + librosa.display.specshow).
 
Topic 2 — ASR and Machine Translation:
- ASR (speech-to-text) converts a continuous signal into discrete symbols; it does not interpret
  meaning. History: Audrey (1952 digits) -> IBM Shoebox (1962) -> Harpy (1971, ~1,011 words) ->
  HMMs (1980s) -> deep learning / Siri (2011) -> WaveNet (2016) -> LLM integration (2020) ->
  enterprise E2E multilingual models (2022).
- Difficulties: device/channel, background noise, speaker differences, similar pronunciations,
  accent/dialect, pronunciation variation in continuous speech (read vs spontaneous), prosody,
  words with multiple pronunciations ("read" /ri:d/ vs /red/), reverberation, overlapping sources.
- Reference WERs (~2020, Jurafsky & Martin): LibriSpeech clean 1.4%, other 2.6%; Switchboard
  (strangers on phone) 5.8%; CALLHOME (family on phone) 11.0%; CORAAL sociolinguistic interviews
  27.0%; CHiME5 dinner party body-worn mics 47.9%, distant mics 81.3%. Mandarin CER: AISHELL-1 read
  6.7%, HKUST telephone 23.5%. Lesson: the same technology spans 1% to 80% error depending on
  speaking style, channel and mic distance — "human parity" on Switchboard does not transfer.
- Classical framework: argmax_W P(W|O) = argmax_W P(O|W)·P(W) — acoustic model (how likely the
  signal corresponds to a sound-unit sequence) x language model (how likely the word sequence is).
  Full hybrid pipeline: preprocessing -> features -> acoustic models (GMM, later DNN) ->
  pronunciation models (dictionary/tables) -> language models (n-gram). Phonemes are the smallest
  meaning-distinguishing units (~44 in English; "cat" = K AE T).
- Machine Translation: benefits (real-time, large scale, localisation, cost) and challenges —
  word-order variation (SVO English vs SOV Japanese; adj/noun order FR, time/place order ZH,
  possessor order MS), catastrophic errors (profanity, violent content, meaning reversal,
  mistranslated proper names), cross-sentence context and pronoun co-reference. SMT framework =
  translation model P(S|T) x target language model P(T); modern NMT learns P(T|S) end-to-end and is
  now standard.
- E2E ASR: one model maps waveform to words — single objective consistent with the ASR goal,
  simpler pipeline, compact enough for on-device, now state of the art and mainstream in industry.
  Three families:
  * CTC — encoder + softmax per frame, inserts blanks and allows repeats so path length matches
    input; frame independence assumption; best combined with an external LM; streaming natural;
    revived by Transformer encoders and self-supervised pretraining.
  * AED (attention-based encoder-decoder, "Listen, Attend and Spell") — flexible reordering, widely
    used for MT; offline by nature, streaming needs extra work (MoChA, MILk chunkwise attention);
    weak on long form. LAS needs lots of data: at 2,000 h it trailed a hybrid CLDNN-HMM (14.1 vs
    8.0 clean WER; 10.3 with LM rescoring); at 12,500 h it beat the conventional system (5.6 vs 6.7)
    with a 0.4 GB model vs 7.2 GB of AM+PM+LM.
  * RNN-T / Transformer Transducer — encoder + prediction network + joint network; LM integrated,
    monotonic alignment, streams output as you speak; the most popular E2E model in industry where
    streaming ASR is required. Encoder options: LSTM -> Transformer -> Conformer (Transformer's
    global context + CNN's local patterns).
- BPE subword units sit between word-level (huge vocab, OOV) and character-level (long sequences):
  "unhappiness" -> un+happi+ness; used for ASR outputs and both sides of MT.
- Foundation models / self-supervised learning: paradigm shift ML -> DL -> foundation models (one
  pretrained base adapted to many downstream tasks). Whisper (680k hours supervised
  multilingual/multitask; encoder-decoder Transformer over log-mel spectrograms; special tokens
  select language, transcribe vs translate-to-English, timestamps or not, and a "no speech" path
  that doubles as VAD; previous text can be passed as a prompt for custom vocabulary; sizes 39M,
  74M, 244M, 769M, 1550M). Wav2Vec 2.0 (self-supervised: CNN encoder -> masked latent frames ->
  Transformer, trained contrastively to match quantised targets; then fine-tuned with CTC; 960 h
  labelled -> 1.8/3.3% WER, 100 h -> 2.0/4.0%, 10 minutes -> 4.8/8.2%, i.e. near-usable ASR from
  10 minutes of labels — the low-resource argument). Two-stage SSL recipe: pretrain an upstream
  model on unlabelled audio, then freeze it or fine-tune it per downstream task (ASR, speaker ID,
  emotion, diarization, intent, slot filling — S3PRL's unified upstream/downstream interface).
  HuBERT, data2vec. Toolkits: FAIRSEQ, S3PRL, ESPnet, SpeechBrain. SSL learns from unlabelled data
  cheaply, helps low-resource ASR, and transfers to speaker/emotion recognition and separation.
- Training issues: resources = transcribed speech (thousands of hours; some systems 60k+),
  pronunciation dictionary, large text corpus; split train/dev/test, tune on dev, report on test;
  diverse data (accents, dialects, rates, noise), augmentation (time-stretch, pitch-shift, added
  noise), accurate transcription. Modelling-unit guidance: very phonetic languages (Spanish,
  German) letter/BPE; reasonably phonetic (English) BPE preferred; non-phonetic (Chinese) use a
  pronunciation dictionary. Most modern ASR/MT is fine-tuned from large pretrained models rather
  than trained from scratch; external LMs combine with E2E models via shallow fusion for domain
  adaptation.
- Metrics: WER = 100*(Substitutions + Insertions + Deletions)/N_words (CER or syllable error rate
  for some languages); WER assumes all errors are equal and mismatches the training objective, so
  task-specific measures (task completion, concept error rate) are also used. MT: BLEU (n-gram
  precision vs human reference with brevity penalty, usually BLEU-4; drops with sentence length).
- Other considerations: domain adaptation (fine-tune on medical/legal data), online learning for
  evolving applications, robustness to noise, environment-specific acoustics (indoor/outdoor).
- Deployment: free text (large-vocabulary dictation/dialogue, usually cloud) vs limited voice
  commands (small, embedded); cloud (huge models) vs embedded (small footprint); near-field
  (phone/PC) vs far-field (smart speaker, echo); channel/sampling rate 16 kHz digital vs 8 kHz
  telephony. ASR — multi-thread processing, real-time factor (RTF 0.1 => ~10 users per core),
  shared model memory vs per-user working memory, latency from transfer + decoding. MT —
  throughput, shared weights vs per-request states, batch (latency tolerant) vs real-time
  (subtitling, speech-to-speech, where ASR+MT+TTS latency accumulates).
- Application examples: telephony, medical records, court transcription, call-centre speech
  analytics, voice assistants/smart speakers, voice-controlled devices, in-car, air traffic control.
- Toolkits: Whisper, ESPnet, Wenet, Kaldi (legacy), HTK (legacy). Cloud: Google STT/Translate,
  Azure Speech/Translator, AWS Transcribe/Translate, IBM Watson; Houndify, Wit.ai (ASR); DeepL,
  Meta SeamlessM4T (MT). Workshop tools named in the deck: Whisper and Wav2Vec2.0 for ASR,
  MarianMT for MT.
 
Topic 3 — Integrating ASR with NLP (case studies):
- Post-ASR text needs punctuation/capitalisation restoration and inverse text normalisation before
  downstream NLP.
- Speaker diarization: "who spoke when" — segment and cluster audio so all segments of one speaker
  are grouped, usually layered with ASR output. Applications: multi-party broadcasts/meetings/
  interviews, richer transcripts (legal, medical), voice assistants distinguishing the primary user
  from background speech. Challenges: overlapping speech, within-speaker variability (emotion,
  illness, room acoustics), short speaker turns. Metric: Diarization Error Rate = missed speech +
  false alarm + speaker error (lower is better).
- Voice search: ASR output must be normalised to what the text search engine expects
  ("iPhone sixteen sixty four g b" -> "iPhone 16 64GB"), plus brand/product-term optimisation
  ("Real me" -> Realme, "Red me" -> Redmi).
- Customer-service quality control: agent/customer sentiment from both text and voice
  characteristics (pitch, loudness), non-talk time, talk speed, interruptions (still hard).
- Speech translation: cascade (ASR->MT->TTS) vs end-to-end. Practical challenges: misrecognitions
  propagate, OOV/domain terms, low-resource languages, disfluencies ("um", "uh"), bad segmentation,
  latency vs accuracy. Cascade-vs-E2E heuristic: integration fails when components evolve on
  different timelines, repair is costly, users want flexibility, integration adds fragility, the
  stack is proprietary/closed; it succeeds when components evolve together, the system is cheap to
  replace as one, users want simplicity, integration adds capability, and it is cloud-updatable.
  Simultaneous ST methods: re-translation (costly, unstable), wait-K (fixed K words, inflexible),
  E2E AED (streaming still hard); dynamic sentence-boundary detection and wait-info policies;
  subtitles must be readable in limited time, dubbing must sync to mouth movement. SM^2 = weakly
  supervised streaming multilingual model doing both ST and ASR, small enough for devices.
- Meeting transcription and summarisation (Otter.ai, Zoom AI Companion): evaluated with BLEU and
  ROUGE. Challenges: misrecognitions, domain terms, disfluencies, speaker attribution, co-reference
  of vague references ("this", "those things"), and disagreement over what is "important".
- Speech LLMs: prepend audio embeddings to text token embeddings so a text LLM performs ASR — a
  conformer encoder (CTC-trained, outputs stacked/projected to the LLM's dimension, e.g. 240 ms
  embeddings) in front of LLaMA-7B beat monolingual baselines by 18% and did multilingual ASR
  despite LLaMA being English-heavy; the LLM can be frozen, LoRA-adapted or fully fine-tuned.
  AudioPaLM fuses text and speech LMs into one decoder-only model over audio+text tokens (with
  SoundStorm/AudioLM for audio output), strong on speech translation including zero-shot
  speech-to-text for unseen language pairs.
- Production GPU considerations: tokens per second (TPS), time to first token (TTFT), GPU sizing
  (T4 16GB works for 3B-8B models), quantisation/distillation, small models with few-shot
  prompting. Closing slide: Gartner hype cycle.
 
--- DAY 3 — WHAT TO KNOW FOR THE EXAM (synthesis, written 2026-09-26) ---
Speech is pass-level in the study plan; the exam is open-book, case-based, output-interpretation,
no code or hand calculation. So the minimum is: be able to design a speech pipeline for a case,
defend the choices from case facts, and read an ASR/diarization/MT output.
 
Decision rules (case signal -> choice -> because):
- Voice interface needed at all? Speech adds ASR error on top of NLU error; use it when hands/eyes
  are busy (car, phone line, accessibility) or the channel is already audio (call centre).
- Pipeline (ASR -> NLU/LLM -> TTS) vs end-to-end: pipeline when components will change separately,
  you need to inspect/repair the transcript, or you reuse an existing text bot (e.g. the Day 1
  Student Life Assistant); E2E when latency and simplicity dominate and the whole model can be
  swapped (Day 3 cascade-vs-E2E table).
- Streaming (live assistant, dictation, live captions) -> RNN-T / transducer (or CTC); offline
  batch (meeting minutes, call audits) -> AED/Whisper-style models are fine and often more accurate.
- Little labelled audio / low-resource language or accent -> self-supervised model (wav2vec 2.0,
  HuBERT) fine-tuned on small data; broad multilingual out-of-the-box -> Whisper; domain jargon
  (bank products, drug names) -> domain fine-tuning or external LM via shallow fusion, plus
  post-ASR normalisation / custom vocabulary.
- Telephone audio is 8 kHz; most modern models expect 16 kHz. A mismatch silently hurts accuracy —
  resample and, if possible, adapt on telephony data.
- Cloud vs on-device: privacy/regulation (banking, health), offline need and cost favour embedded
  small models; large-vocabulary free text favours cloud.
- Multi-speaker audio (meetings, calls) -> add diarization before attributing statements;
  customer-service QA -> combine text sentiment with acoustic cues (pitch, loudness), talk speed,
  silence, interruptions.
- Always post-process ASR text before NLP: punctuation/casing restoration, inverse text
  normalisation ("sixty four g b" -> "64GB"), filler removal, entity correction.
 
Outputs to be able to read:
- WER line or table: WER = (S + I + D) / N_reference, so it can exceed 100% via insertions.
  Diagnose by error type: many deletions -> low volume/far-field/VAD cutting speech; many
  substitutions on names/jargon -> domain gap (custom vocab, LM fusion, fine-tune); insertions on
  silence -> hallucination/noise. WER treats "a"/"the" errors the same as a wrong account number, so
  for a task bot also report task success or concept (slot) error rate.
- Same model, different conditions (the Jurafsky table): big WER jump from clean read speech to
  conversational or distant-mic audio = mismatch between training and deployment conditions, not a
  bad model. Fix the data/channel, not the architecture.
- Text normalisation trap: two systems whose transcripts differ only in casing/punctuation can
  show very different WER unless both reference and hypothesis are normalised first.
- DER = missed speech + false alarm + speaker confusion; high confusion with short turns/overlap
  is expected; a meeting summary built on wrong speaker labels misattributes decisions.
- BLEU for MT: n-gram overlap with a reference plus brevity penalty; low BLEU on one valid
  paraphrase is not necessarily a bad translation; in a cascade, check ASR WER first — MT cannot
  recover words ASR lost.
- Latency: real-time factor (RTF < 1 needed for live use; RTF 0.1 ~ 10 streams per core); in
  speech-to-speech, ASR + MT + TTS latencies add up.
 
Traps: ASR "does not understand" (no meaning at this stage); lower WER is better but not the
business metric; human-parity headlines come from one benchmark; E2E still benefits from an
external LM for rare domain words; Whisper-style models can hallucinate fluent text on silence or
noise; diarization and ASR errors compound in summaries.
 
Project link: the team chatbot is text-only, so none of this is required for the Practice Module.
If a voice front end were ever added, it would sit in front of the same RAG bot (pipeline), with
ASR errors on ticker/bank names (DBS, OCBC, UOB) as the obvious failure mode to test.
