The corpus aspect run: when it has to be redone

llama3.1:8b gave each of the 44,345 sentences one aspect (finished 14:04 on Sat 3 Oct), saved to data/aspect_llm/llama3.1_8b.96efe244.jsonl; nothing in the database changes. The answers are only good for the exact question the model was asked, so changing that question means starting again, which takes the MacBook about a day.

Donethe run finished14:04 on Sat 3 Oct: all 44,345 sentences, no invalid answers.
~1 dayfor a full redoAll 44,345 sentences again. Longer if other jobs run on the Mac at the same time.
<1 hto test a new wording firstThe 1,277 labelled sentences, scored against the human aspects.
Nothinglost on a stop or crashThe same command resumes, and new data only adds its own sentences.

Redo from scratch when

  • an aspect is added, removed or renamed in config/aspects.yaml
  • an aspect's definition or a worked example changes: llm_definition and llm_examples in config/aspects.yaml are the prompt
  • the model changes

The code notices all three by itself and starts a new file.

No redo for

  • a stop, crash or reboot: the same command resumes where it stopped
  • new sentences: only they are classified
  • the scoring model, NER and DBS Vickers, passing mentions, chatbot settings, how the index is blended

Fixed on 2 Oct: the cache file is named by a hash of the prompt (96efe244 is today's wording). Before, a reworded prompt silently reused the old answers, so a "new" score was really the old one. Now a changed wording starts a new file, the old answers stay in theirs, and undoing the change picks the old file up again. Each run prints the file it uses.

To try a new wording:

  1. Stop the current run or let it finish: two jobs on the Mac's GPU slow each other.
  2. Edit the definitions or examples in config/aspects.yaml (llm_definition, llm_examples).
  3. Test, under an hour: .venv-plp/bin/python3 -m aspects.llm_classify --eval. Compare with 0.729 top-1 and wealth F1 0.50 today.
  4. Better: redo the corpus, about a day, with caffeinate -i .venv-plp/bin/python3 -m aspects.llm_classify --corpus --model llama3.1:8b. Not better: undo the edit; the old answers are used again.

A redo started by Fri 9 Oct still finishes before the 12–18 Oct re-score week. While it runs, other local-model jobs (chatbot evaluations, the judge) share the Mac: running them alongside slows both and has caused timeouts.

  • Decide whether the LLM's aspects replace the centroids, and choose the disagreement rule Decision by 5 Oct

    Why: the database's aspects come from seed centroids, which give a sentence about 6.4 aspects and match the human's aspect only 41% of the time; llama3.1:8b matches 73%, and 84% where qwen3:4b agrees. Every per-aspect claim in the report depends on this. Choose with it what happens to the 24% of sentences where the two models disagree: keep llama's answer, or mark them other.

    Unblocks: the re-score. The corpus run is done (3 Oct), and the full-corpus preview is in the index-preview evidence. Source: llm-aspect-classifier, index-preview.

    Why: DBS Treasures, OCBC Premier and unit trusts bought at a bank are the boundary behind 63 of Opus's aspect disagreements, and wealth is one of the classifier's weakest aspects (F1 0.50).   • Decide the scoring model: the fine-tuned models, or base FinBERT Decision by 12 Oct

    Why: the stored scores are base FinBERT's, so the DNN the rubric requires doesn't yet affect what the product shows. The 1 Oct seeds were trained from a relabelled head (a bug, fixed 3 Oct). Retrained on 4 Oct, every seed beats base FinBERT (test macro-F1 0.646, 0.592 and 0.625; mean 0.621 ± 0.027 against 0.571), and the average of the three matches base on accuracy (0.702 against 0.699). On the full corpus the retrained average barely moves the headlines (within 0.015 of base with the margin: DBS +0.132, OCBC +0.122, UOB +0.084) and agrees with base FinBERT on every aspect's sign; seed 42 alone still raises every headline, so the level depends on the seed. Two choices: the retrained seeds or the 1 Oct ones, and whether to keep the neutral margin. Tuned on dev for the averaged model, the margin is 0.10 (a single-model stand-in: no clean dev set exists for the three-seed average); on test it makes no measurable difference (0.612 against 0.634 at argmax, paired bootstrap interval −0.058 to +0.009), and the test result can't be used to drop it: keep 0.10 and report argmax beside it. State the criterion first. For the report: the input change chosen on 1 Oct proved no better on two more seeds, so credit no single change for the gain.

    Source: retrain and ensemble-margin (4 Oct), finetune-fixes, error-analysis, index-preview, noise-floor-cv. Decision 7 in the decision brief. scripts/rescore.py still defaults to the 1 Oct seeds.
